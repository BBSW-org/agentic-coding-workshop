1  The Whole Game

Spoiler alert!

This chapter runs through the whole game of working with a coding agent: posing a problem, letting the agent solve it, and deciding when it is done. It is meant to paint the big picture and suggest a way of thinking, before we get into the details in the rest of the book.

When producing code is no longer the bottleneck, the bottleneck becomes deciding what to build and knowing when it is right. For that, we borrow a framework you already know from sparse linear models: structured optimization.

1.1 Agents are models using tools

A coding agent is a language model that uses tools. You describe what you want first. The agent reads files, writes code, runs it, looks at the result, and decides what to do next. It repeats this inexplicit loop until it decides the job is done.

As of 2026, there are three key components that make this loop work:

  • The model does the inference. It reads everything so far and proposes the next action.
  • The harness is the runtime around the model. It supplies the tools (read, edit, search, run commands) and drives the loop: reason, act, observe, repeat (Yao et al. 2023).
  • The prompt is what you tell the model about your problem.

If you have implemented IRLS or EM, you know this shape: propose a step, evaluate it, update, check for convergence. The model is the solver. The harness is the algorithm that runs it. Both improve every few months without any help from you. But neither knows what problem you want solved. That part is yours, and it is what the rest of this chapter is about.

Note that we don’t tell the agent how to use its tools. The goal is to let the model figure that out. Never try to do its job for it!

1.2 Structured optimization

There is a useful way to think about sparse linear models that is not quite a theorem, but is close enough to be worth keeping in your head:

\[ \text{fit the data} \ + \ \text{prefer simple structure} \ + \ \text{only allow reasonable answers}. \]

In more statistical notation (Negahban et al. 2012):

\[ \hat\beta \in \arg\min_{\beta \in \mathcal C} \left\{ \mathcal L_n(\beta) + \lambda \mathcal R(\beta) \right\}. \]

  • \(\mathcal L_n(\beta)\) is the objective: squared error, negative log-likelihood, negative log partial likelihood. It says: please explain the data.
  • \(\mathcal R(\beta)\) is the regularizer: \(\|\beta\|_1\) for the lasso, something more opinionated for the group lasso, fused lasso, and friends. It says: yes, but not in a ridiculous way.
  • \(\mathcal C\) is the constraint set: nonnegative coefficients, monotone fits, interactions only alongside their main effects. These are world rules.

The statistical model picks the loss. Prior knowledge picks the regularizer. The problem picks the constraints. A solver does the rest.

1.3 From linear models to coding agents

When we ask a coding agent to do something, a lot of things happen beyond just talking to a model. We are posing an optimization problem to a strange, stochastic, tool-using solver:

\[ \widehat{\text{code}} \in \arg\min_{\text{code} \,\in\, \text{environment}} \left\{ \text{task} + \lambda \cdot \text{context} \right\}. \]

1.3.1 Context is soft, environment is hard

The difference between the last two terms matters as much here as it does in the lasso. Context is soft. The model weighs it against the task and sometimes decides your preference isn’t worth the trouble. The environment is hard. A test passes or it doesn’t.

This leads to the most practical advice in this chapter: if something is non-negotiable, don’t just say it, check it. A constraint that only lives in the prompt is a regularizer.

The output is broken, but in a way that’s getting harder and harder to detect. Which is exactly what you would expect from an increasingly accurate statistical model.

— George Hotz, The Eternal Sloptember

Reading the output and nodding along doesn’t scale. Our industry figured this out long before LLMs: we don’t trust a table until an independent program reproduces it. The environment is your QC programmer, and it never gets tired.

1.3.2 Choosing \(\lambda\)

\(\lambda\) sets how hard you lean on context, and the right value depends on the task. Patching a mature codebase calls for a large \(\lambda\): the fix should look like it was always there. Exploratory research calls for a small one: let the model roam. Building from scratch sits in between, and the prompt spends most of its words on the task and the environment instead.

1.4 The whole procedure matters

The model proposes actions. The tools execute them. The environment evaluates them. The next action depends on what happened before. At that point, we are designing a procedure.

As statisticians, we should be very comfortable with that idea. We would never judge a group sequential design by its final test statistic alone; its operating characteristics depend on the stopping boundaries. Likewise, what an agent delivers depends on the whole procedure: the prompt, the files it sees, the examples, the tools, the tests, the error messages returned, and the stopping rule. Of course the model matters a lot, but the procedure matters more than people often admit.

This is why agentic engineering is more than plumbing. The job is to turn a vague request into a well-posed problem.

1.5 Fewer words

There are endless ways to write a prompt. Our goal is to express intent in as few words as possible.

A prompt is fit to one model: the one you are using today. Pile on tricks tuned to its quirks and the prompt overfits. It breaks when the model’s tendencies shift or its capabilities jump. Occam’s razor applies. If the model is smart enough, it will find its own path up the mountain. Our job is to say why we are climbing, where the summit is, and what gear is in the pack.

In practice, the first prompt should one-shot the task or, at least, get its general shape right. Follow-up prompts should only fix the details.

It helps to keep a personal prompt library: first prompts that worked, and notes on the ones that didn’t. The template below summarizes how we write first prompts.

1.6 A prompt template

The template has one section per term in the problem.

## Context

High-level goal of the project, and of the part we are working on.
What already exists, what's missing, and what needs to be done.

Domain metadata: what the output looks like, and the usual way to do it.
Institutional knowledge, or where to find it.
Special requirements, especially anything out of distribution.
Lessons from past sessions: corrections, mistakes not to repeat.

## Task

Your high-level task is to [insert task here].

1. Specific subtask, with the files to read (@path/to/input) and write.
2. ...

How to verify the task is complete: tests to run, metrics to hit.
Quality loop: lint, test, document.
Record guidelines for future agents in `AGENTS.md`.

## Environment

- A map of the existing codebase, if any.
- Source code of reference projects under @deps-src/.
- What is already installed. Ask before installing anything new.
- The package manager and how to run commands.
- Frameworks, libraries, and tools to use, with versions if they matter.
- Real-world considerations, such as parallelism and error handling.

A few notes:

  • We lead with context, the way you would brief a new colleague: background first, then the ask.
  • The task section says what done means. The environment section supplies the machinery that checks it.
  • Not every section needs to be long. Their lengths follow \(\lambda\) and the type of task.
  • Some harnesses remember lessons across sessions. If yours doesn’t, or you are starting fresh, put the lessons in context.
  • AGENTS.md is a file many coding agents read at the start of every session. Keeping it updated means the next session starts with context instead of from scratch.
TipTagging files

Most coding agents let you point at a file or directory with @, as in @data/adsl.parquet. Name the files to read and write as precisely as you can. Every file the agent doesn’t have to search for is one fewer chance to pick the wrong one.

1.7 Toy task: demographics table

To make this concrete, here is a first prompt for a table every industry statistician has made by hand: demographics. The task is deliberately small. We are only using it to show the template in action.

## Context

We are building a small Python package that produces clinical trial
summary tables as RTF files. This is its first table. Nothing exists
yet beyond the project skeleton and an ADSL dataset at @data/adsl.parquet.

The demographics table summarizes age, sex, and race by actual treatment
(`TRT01A`) for the safety population (`SAFFL == "Y"`). Age shows n,
mean (SD), median, and min, max. Sex and race show n (%), with the
arm's N as the denominator.

Keep it simple: a few plain functions, no classes.

## Task

Your high-level task is to create the demographics table.

1. Write the summary logic in `src/agentic_coding_workshop/demog.py`.
2. Write the table to `output/demog.rtf` with rtflite.
3. Write tests in `tests/test_demog.py` that check every count and
   percentage against an independent computation.

You are done when `uv run pytest` passes and `uv run ruff check` is clean.
Then record what a future session should know in `AGENTS.md`.

## Environment

- Use uv for dependencies and commands.
- polars and rtflite are installed. Add pytest as a dev dependency.
  Ask before adding anything else.
- The rtflite source is under @deps-src/rtflite/ if you need its API.

Read as an optimization problem:

  • Objective: create the table, broken into three subtasks with named files.
  • Regularizer: plain functions, no classes, plus the display conventions.
  • Constraints: pytest passes, ruff is clean, and the tests check every count and percentage against an independent computation.

Notice that the display conventions start out as prose, which makes them a regularizer. The third subtask promotes counts and percentages to constraints. That’s double programming, delegated.

A typical run goes like this. The agent inspects the data, writes the summary code and the tests, runs them, reads the failures, fixes the code, and stops once everything passes. Occasionally, it “fixes” a failing test instead. That’s the agent relaxing your constraint set, so read the diff.

Then you open output/demog.rtf.

1.8 The unknown knowns

Now the table looks right and the tests pass. And yet:

  • Mean and SD have the same number of decimals, but your house rule gives the mean one more decimal than the raw data and the SD two more.
  • Race categories are sorted alphabetically, not in CRF order.
  • There is no “Missing” row, so the race percentages don’t add up to 100.

Nothing in the prompt said otherwise. These are unknown knowns: things you know so well that you never think to say them. They are also the limit of this framework. The agent solves the problem you wrote down, not the one in your head. A constraint you never wrote down isn’t in \(\mathcal C\), and the solver will happily return an optimal answer to the wrong problem.

You can’t list what you don’t know you know, but you can shrink the set:

  • Ask the agent to state its assumptions, or to ask you questions before it starts. An assumption written down is one you can review.
  • Fold every correction back into context, as a line in AGENTS.md or in the agent’s memory. Pay for each lesson only once.
  • Promote the ones that matter to the environment. If decimal precision is a rule, write the test.

Then send the follow-up:

Format age by our precision rule: mean and median get one more decimal
than the raw data, SD gets two more. Order race categories by `RACEN`
and add a "Missing" row. Add tests for both.

One prompt for the general shape, a few follow-ups for the details.

1.9 Review

This chapter is meant to give you a sense of how to work with a coding agent, summarized in Table 1.1.

Before you hit enter to submit prompts to a coding agent, ask three questions:

  1. Task: What do I want done, and how will we know it is done?
  2. Context: What should a good solution look like, and what would a new colleague need to know?
  3. Environment: What can the agent use, and what must it never violate?

And keep a few habits:

  • Let the model decide how to use its tools.
  • Context is soft, the environment is hard. If something is non-negotiable, check it.
  • Tune \(\lambda\) to the task.
  • Write fewer words. Don’t overfit the prompt to today’s model.
  • Hunt for unknown knowns, and fold every correction back in.

The rest of the book goes into greater detail on each piece. Vibe coding (Chapter 3) is about writing tasks and context. Agentic workflows (Chapter 4) chain many such problems together. Harness engineering (Chapter 5) builds the environment: the checks that turn preferences into constraints. Governance (Chapter 6) makes the whole procedure auditable.

The task defines what we want.

The context defines what kinds of solutions we prefer.

The environment defines what it means to be done.
